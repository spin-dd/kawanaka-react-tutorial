# カリキュラム全体像

このドキュメントは、学習の全体像を示すものです。
Issue は 1 つずつ作りますが、作る側（教育担当）が全体像を見失わないように、ここに「何を、どの順で、なぜ」学ぶかをまとめています。
学習者が読んでも構いませんが、先回りして実装する必要はありません。Issue が来てから取り組んでください。

## ゴール

- **最終ゴール**: 実務のリポジトリで「この画面がこう動くのはなぜか」を、コードを辿って自力で説明できるようになる。
- **そのための中間ゴール**: 小さなアプリ（月次締めつきの小遣い帳）を、ゼロから実務と同じ構成まで自分の手で育てる。
  目標成果物は [`goal/kozukai-sample.html`](./goal/kozukai-sample.html) を参照。

## 運用ルール

- 教育担当が Issue を 1 つ作り、学習者は **1 Issue につき 1 PR** を出す。
- Issue は先にまとめて作らない。レビューで見えた課題を次の Issue に反映する。
- 実装の効率より、「なぜそう書くのか」を自分の言葉で説明できることを優先する。
- 学習のチャンスがあれば、本筋から少し外れていても Issue にして組み込む。
- 各 Phase の最後に、教育担当との **面談** を行う。面談では「自分の言葉で説明する」ことを求める。

## Issue の書式

教育担当が Issue を作るときは、次の構成に揃える。

```
## 目的        この Issue で何を身につけるか（2〜3 行）
## やること     手順。番号付き。ファイル名・配置場所を明示する
## 完了条件     チェックボックス。動作・構成・PR の記述の 3 観点
## 確認問題     PR の説明欄に自分の言葉で書かせる質問（3〜5 問）
## 注意        ディレクトリ規約、やってはいけないこと、30 分ルール
```

- 前提となる Issue がある場合は、冒頭に「この Issue は #N が終わってから取り組んでください」と書く。
- 確認問題には、必ず 1 問は「どこで使われているか、どうやって調べたか」のような **辿る練習** を入れる。
- 設定作業など PR を伴わない Issue は、報告を Issue のコメントで行わせ、教育担当が閉じる。

## ディレクトリ規約

| 場所 | 置くもの |
| --- | --- |
| `src/pages/` | 画面そのもの |
| `src/components/` | この画面のための部品 |
| `src/shared/ui/` | どの画面でも使える汎用の部品（Card、Button、Dialog など） |
| `src/utils/` | React に関係ない、ただの関数 |
| `src/data/` | 固定データ（API ができるまでの仮データ） |
| `src/types/` | 型定義 |

Phase 9 でレイヤー構成に組み替えるまでは、この規約で進める。

### Phase 0: 環境

**学習目標**: プロジェクトの土台と、PR を経由する開発の流れを体に入れる。

| Issue | 内容 | 状態 |
| --- | --- | --- |
| 課題 0 | Vite + React + TypeScript でリポジトリを作り、main を push する | 完了 |
| #1 | Tailwind CSS v4 を導入し、テンプレートを消して Hello World を出す | 登録済み |
| #6 | main への直接 push を禁止する（リポジトリ設定） | 登録済み |

差し込み候補: oxlint の設定を読む、Prettier の導入、`tsconfig` の `strict` を確認する。

### Phase 1: props だけで画面を組む

**学習目標**: state を使わずに、コンポーネントの親子関係と props の流れだけで画面を作る。「どこで使われているか」を辿る練習を繰り返す。

| Issue | 内容 | 状態 |
| --- | --- | --- |
| #2 | 固定データで明細一覧を表示する（ページ → 一覧 → 1 行、`map` と `key`、`Entry` 型） | 登録済み |
| #3 | console.log で描画の流れを追う（順番・回数・StrictMode） | 登録済み |
| #4 | サマリカード（収入・支出・残高）。派生値、`formatYen` の共通化 | 登録済み |
| #5 | カード部品を作る（`children` を受け取る部品） | 登録済み |

### Phase 2: state とイベント

**学習目標**: `useState` と制御された入力で、画面が操作に反応するようにする。state をどのコンポーネントが持つかを考える。

Issue 候補（この順）:

1. **月の切り替え**: 表示月を state に持ち、前月・翌月ボタンで切り替えて明細を絞り込む。「今月」バッジ。固定データを 9 月・10 月・11 月に増やす。
2. **明細の追加フォーム**: 一覧の上に直接フォームを置く（ダイアログにはまだしない）。制御された入力、`onSubmit`、state の持ち上げ（配列は `Home` が持ち、フォームには追加関数を渡す）。入力チェック（必須、金額は 1 円以上）は if 文で手書きする。ライブラリ（zod）は Phase 4 で入れる。
3. **console.log で入力値の正体を確かめる**: `e.target.value` と `typeof`。`type="number"` でも文字列であること。合計が文字列連結で壊れる場面を自分で見つけて直す。
4. **明細の削除**: 配列を直接書き換えず、`filter` で新しい配列を作る。削除は確認なしでよい（確認ダイアログは Phase 4）。
5. **条件レンダリング**: 未分類があれば警告バナー、明細 0 件なら空表示。
6. **デバッグ課題 1**: 教育担当が条件を 1 箇所壊したブランチを渡し、原因と理由を PR で説明する。

### Phase 3: ロジックの分離

**学習目標**: コンポーネントからロジックを切り出し、カスタムフックと真偽値にまとめる。「表示は state の関数」を体に入れる。

Issue 候補（この順）:

1. **`useLedger` フック**: 明細の配列と追加・削除・更新の関数をカスタムフックにまとめる。フックは「ただの関数」で、定義へ移動で中身が読めることを確認する。
2. **「今月を締める」ボタン**: 締め済の月を state に持つ。表示条件（表示月が今月、未締め、未分類なし）を `canClose` という真偽値にして、`Button` の `show` に渡す。締め済の月は追加・削除できない。
3. **締めは月の順番どおりに**: 「前月が締め済（前月に明細がなければ不要）」を `canClose` の条件に加える。条件が増えても if の入れ子にならない書き方を考える。前月の状態という「表示中の月の外」の情報が必要になることを確認する。
4. **console.log でボタンが出ない理由を特定する**（デバッグ課題 2）: 教育担当がボタンが出ないブランチを渡す。条件の材料をオブジェクトでまとめて出力し、偽の材料まで遡る。経路を PR に書く。

### Phase 4: 詳細・編集・ダイアログ

**学習目標**: 画面を増やし、フォームを共用し、ダイアログを部品化する。入力チェックを zod のスキーマに寄せる。composition（`children`）を実戦で使う。

Issue 候補（この順）:

1. **明細詳細ページ**: 行の内容をクリックすると詳細に切り替わる。切り替えは state（`page`）で行う（ルーターは Phase 7）。編集・削除の導線は詳細ページにだけ置き、一覧からは外す。
2. **備考（textarea）**: 明細に `note` を追加。制御された textarea、文字数表示（200 文字上限）、詳細での改行表示（`whitespace-pre-wrap`）。入力チェックはまだ手書きのまま。項目が増えて if 文が増えていくのを体験する。
3. **zod でフォームの入力チェックをスキーマにする**: `zod` を導入し、手書きの if 文を 1 つのスキーマ（`entryFormSchema`）に置き換える。必須、1 円以上、200 文字以内、日付の形式をスキーマで表現し、`safeParse` の結果からエラーメッセージを項目ごとに表示する。スキーマから `z.infer` で型を導き、`Entry` 型との関係を整理する。実務のリポジトリでも、フォームの入力形式の検証は zod スキーマで行う。
4. **スキーマに書けない業務ルール**: 次の 2 つのルールをフォームに追加する。どちらもスキーマには書かず、純粋な関数（例: `getDateRegistrationError`、`getNoteRequirementError`）にして、フォームから呼ぶ。
   - 明細の日付は、締め済の月と、今月より先の月には登録できない（編集で動かすのも不可）。判断には締め状態と今月が必要で、フォームの値だけでは決められない。
   - 10,000 円以上の支出は備考が必須。金額と備考という 2 つの項目をまたぐ判断。閾値は定数にする。一覧と詳細には「高額」バッジを出す。
   「入力形式の検証（スキーマ）」と「業務ルールの判断（関数）」を分ける理由を、確認問題で自分の言葉で言わせる。
5. **`FormField` 部品**: ラベル・入力欄・エラーの組を `children` を受け取る部品にする。input / select / textarea / ラジオの組が同じ枠に入ることを確認する。エラーメッセージは、スキーマの結果と業務ルールの結果のどちらも同じ形で渡す。
6. **Headless UI の導入と `Dialog` 部品**: `@headlessui/react` を入れ、開閉・Esc・背景クリック・フォーカス復帰を担う枠 `Dialog` を作る。
7. **確認ダイアログ**: `Dialog` を使って `ConfirmDialog` を作り、締めと削除に挟む。削除対象の情報をボタンからダイアログまでどう渡すかを考える。
8. **追加・編集フォームをダイアログに**: 追加フォームをダイアログに移し、同じフォームを編集にも使う（初期値の有無でモードを分ける）。スキーマは追加と編集で共用する。

### Phase 5: 非同期

**学習目標**: `useEffect` と Promise で、画面の外からデータが来る状況を扱う。読み込み中とエラーを区別する。

Issue 候補（この順）:

1. **localStorage への保存と復元**: 明細と締め状態をブラウザに保存し、再読み込みしても残るようにする。`useEffect` の依存配列。
2. **偽 API から「今月」とカテゴリ一覧を取得する**: `setTimeout` や Promise で遅延する関数を `src/api/` に置き、読み込み中とエラーの状態を持つ。「データ未着で出ない」と「条件不一致で出ない」を区別する。
3. **カテゴリ別の月予算と超過警告**: 予算（カテゴリごとの月額）を偽 API から取得し、表示中の月の支出と比べて「カテゴリ別予算」カードに消化状況を出す。超えたカテゴリには「超過」バッジと警告バナーを出す。超過は警告だけで、締めは妨げない。「外から来るデータ（予算）」と「それを使った判断（超過しているか）」を別の関数に分けておく。

### Phase 6: Context

**学習目標**: props のバケツリレーを体験し、`useContext` で解消する。グローバル状態ライブラリ（Phase 7）を入れる動機を理解する。

Issue 候補（この順）:

1. **バケツリレーを体験する**: 「今月」とカテゴリ一覧を、`Home` から詳細ページやダイアログまで props で渡し、何段も経由することを確認する。
2. **`useContext` で配る**: `AppContext`（今月・カテゴリ一覧）を `Provider` で配り、必要なコンポーネントが直接受け取る。中間のコンポーネントから props が消えることを確認する。
3. **`useLedger` を Context に乗せる**: 明細の配列と操作関数も Context で配る。「Context の値が変わると、それを読んでいるコンポーネントが全部再描画される」を console.log で観察する。

### Phase 7: ルーティングとグローバル状態

**学習目標**: URL と画面を対応づけ、状態を atom に移す。「この atom を書いているのは誰か」を探す習慣をつける。表示条件をルール表として読めるようにする。

Issue 候補（この順）:

1. **React Router の導入**: `/ledger/:month` と `/entries/:id` にページを割り当てる。URL とコンポーネントの対応表を作る。`page` の state を URL に置き換える。
2. **Jotai の導入**: Phase 6 の Context を atom に置き換える。atom の定義場所、書き込む場所、読む場所を分けて把握する。
3. **表示条件をルール表にする**: `canClose` などの条件を、`rules` オブジェクトと評価関数に書き換える。条件が増えても if の入れ子にならない形を体験する。
4. **デバッグ課題 3**: 教育担当がルール表の 1 条件を壊したブランチを渡す。atom の書き手とルール表を辿って原因を特定する。

### Phase 8: テスト

**学習目標**: ロジックにテストを書き、何をテストすべきかを選べるようになる。

Issue 候補（この順）:

1. **Vitest の導入と `formatYen` のテスト**: ただの関数のテストから始める。
2. **業務ルールと zod スキーマのテスト**: `canClose` の判定を条件の組み合わせごとにテストする。日付の登録可否、高額支出の備考必須、予算の超過判定も、入力と期待結果を並べてテストする。フォームのスキーマも、通る入力と弾かれる入力を並べてテストする。「React に依存しないロジックはテストしやすい」ことを体感する。
3. **Testing Library でコンポーネントのテストを 1 本**: 「未分類があれば警告が出る」のような、見える挙動のテスト。

### Phase 9: アーキテクチャ

**学習目標**: ここまで「動くもの」として育てたアプリを、実務のリポジトリと同じレイヤー構成（フィーチャーベースの DDD 構造）に組み替える。各レイヤーの責務と、依存してよい方向を理解する。

目標とする構成。小遣い帳は 1 つの feature（`ledger`）として組む。

```
src/
├── features/ledger/
│   ├── core/           # 業務ルール（純粋ドメイン）。React にも API にも依存しない
│   ├── app/
│   │   ├── mapper/     # 境界翻訳（infra の DTO ⇄ ドメイン型）
│   │   ├── usecase/    # 業務処理の手順（締める、追加する、初期化する）
│   │   ├── util/       # 純粋ヘルパー（表示用の変換など）
│   │   └── hooks/      # view と usecase・state をつなぐ hook
│   ├── state/          # Jotai atom の定義だけ
│   ├── view/           # UI コンポーネント
│   └── pages.ts        # ルーティングに載せる画面の公開エントリ
├── domain/             # 複数の feature が共有する業務ドメイン（今回は使わなくてよい）
├── infra/
│   ├── ledger/
│   │   ├── ledger.port.ts        # Port（インターフェース）
│   │   └── ledger.repository.ts  # Repository 実装（localStorage・偽 API）
│   ├── repos.ts                  # Repository 実装をまとめて生成する
│   ├── RepositoryProvider.tsx    # Repository を Context で配る Provider
│   └── useRepos.ts               # Provider から Repository を取り出す hook（usecase の組み立て専用）
├── usecase/
│   ├── container.ts              # Repository を usecase に組み立てる DI コンテナ。配線だけ
│   ├── UsecaseProvider.tsx       # usecase を Context で配る Provider
│   └── useUsecase.ts             # Provider から usecase を取り出す hook（app/hooks から使う）
├── shared/ui/          # feature をまたいで使う汎用の部品。infra・usecase に依存しない
├── pages/              # ルーティング
└── main.tsx            # composition root。RepositoryProvider → UsecaseProvider → App の順に包む
```

Provider の配置は次のとおり。`main.tsx` がアプリ全体を 2 つの Provider で包み（composition root）、それより内側では Provider を作らない。

```
main.tsx
└── <RepositoryProvider>          infra/repos.ts で Repository 実装を生成して配る
    └── <UsecaseProvider>         useRepos() で Repository を受け取り、usecase/container.ts で usecase を組み立てて配る
        └── <App>                 ルーティングと画面。app/hooks は useUsecase() で usecase を受け取る
```

依存の方向:

```
main.tsx ──→ infra/RepositoryProvider ──→ infra/repos.ts ──→ infra/ledger/*.repository.ts
         └─→ usecase/UsecaseProvider ──→ usecase/container.ts ──→ features/ledger/app/usecase

view ──→ app/hooks ──→ usecase/useUsecase() ──→ app/usecase ──→ infra（Port 経由）
                │                                    └──→ app/mapper ──→ core
                └──→ state, core
state はどこにも依存しない。core は外界に一切依存しない。
app/hooks は usecase を useUsecase() 経由で受け取り、app/usecase や infra を直接 import しない。
```

| レイヤー | 責務 | 置かないもの |
| --- | --- | --- |
| `core/` | 業務ルール。可否・要否の判断（「締められるか」「編集できるか」）、金額計算、バリデーション | React、API、infra の型 |
| `app/usecase/` | 処理の流れ。「締める」なら、判断を core に聞き、保存を Repository に頼む | UI、JSX |
| `app/hooks/` | view に必要なものを返す配線。usecase の呼び出しと atom の読み書き | 業務ロジック、Repository の直接呼び出し |
| `app/mapper/` | infra の DTO とドメイン型の相互変換 | 業務判断 |
| `state/` | atom の定義 | ロジック |
| `view/` | 表示と入力の受付 | 可否の判断を生の値から組み立てること |
| `infra/` | 外部とのやりとり。Port（インターフェース）と Repository 実装 | 業務判断 |
| `usecase/`（トップ） | Repository を usecase に注入する DI コンテナ | ロジック |

Issue 候補（この順）:

1. **レイヤーの説明を読み、現状のコードを分類する**: いまのファイルがどのレイヤーに当たるかを表にする。1 つのファイルに複数のレイヤーが混ざっている箇所（view の中で可否を判断している、hook の中で localStorage を触っている、など）を見つける。
2. **core を切り出す**: 業務ルール（締められるか、編集できるか、日付を登録できるか、備考が必要か、予算を超えているか）と金額計算を `features/ledger/core/` に移す。React を import していないことを確認する。Phase 8 のテストがそのまま通る。ルールが 5 つあるので、core にまとまったときの見通しの良さと、view から判断が消えることが実感できる。フォームの zod スキーマは、形を決めているのが画面の入力項目なので core ではなく `app/` に置く。業務ルールとしての判断（未分類があれば締められない、など）はスキーマに書かず core に残す。
3. **infra と Port を切り出す**: localStorage と偽 API を `infra/ledger/` の Repository にし、インターフェース（Port）を定義する。usecase からは Port だけを見る。
4. **usecase と hooks を分ける**: 「締める」「追加する」「初期化する」を `app/usecase/` にし、`app/hooks/` は view と usecase をつなぐだけにする。可否の判断を view や hook から core へ移す。
5. **DI コンテナと Provider**: `src/infra/repos.ts` と `RepositoryProvider` で Repository を配り、`src/usecase/container.ts` と `UsecaseProvider` で usecase を組み立てて配る。`main.tsx` で 2 つの Provider を重ねる。`app/hooks` は `useUsecase()` 経由で usecase を受け取るように直す。テストでは `RepositoryProvider` に偽の Repository を渡して、usecase を変更せずに差し替えられることを確認する。
6. **依存方向を確認する**: 各レイヤーが「依存してよい先」以外を import していないかを確認する。見つかったら直す。

このレイヤー名は実務のリポジトリと同じものなので、Phase 9 を終えると実務のコードを同じ地図で読める。

### 卒業課題

Phase 9 まで終えたら、教育担当が用意する最終課題に取り組む。

方針:

- 題材は **実務のリポジトリ** から選ぶ。「ある操作ボタンが表示されない」「ある値が期待と違う」のように、画面の挙動の原因をコードから辿る課題にする。
- 答えは教えない。学習者は、Phase 3 と Phase 7 で身につけた「表示条件の材料を辿る」「atom の書き手を探す」「ルール表を読む」手順をそのまま使い、辿った経路を自分の言葉で説明する。
- 課題の具体的な内容は、そのときの実務リポジトリの状態を見て教育担当が決める。

## 横断テーマ

Phase をまたいで繰り返し組み込むテーマ。Issue を作るときに「今回どれを入れるか」を確認する。

### console.log によるデバッグ（3 段階）

| 段階 | 内容 | 配置 |
| --- | --- | --- |
| 1 | 描画の順番と回数を観察する | Phase 1（#3） |
| 2 | 入力値の正体（値と型）を確かめる | Phase 2 |
| 3 | 条件の材料を出力して、偽の材料まで遡る | Phase 3 |

共通ルール: ログの先頭に `[コンポーネント名]` を付ける。確認が終わったら消す。消し忘れは後で lint に検出させる（Phase 7 以降の差し込み候補: oxlint の `no-console`）。

### composition（`children` を受け取る部品、3 段階）

| 段階 | 内容 | 配置 |
| --- | --- | --- |
| 1 | `Card`: 繰り返す枠を部品にする | Phase 1（#5） |
| 2 | `FormField`: 中身が input / select / textarea と変わっても枠は同じ | Phase 4 |
| 3 | `Dialog`: 枠が開閉を担い、中身を差し替える | Phase 4 |

共通ルール: 先に繰り返しを数えさせてから部品化する。置き換え後に見た目が変わらないことを完了条件にする。確認問題で毎回「枠は中身を知っているか」を聞く。

### デバッグ課題（教育担当がバグ入りブランチを渡す、3 段階）

| 段階 | 壊す場所 | 配置 |
| --- | --- | --- |
| 1 | 条件レンダリングの条件 | Phase 2 |
| 2 | ボタンの表示条件の材料 | Phase 3 |
| 3 | ルール表の 1 条件 | Phase 7 |

方針:

- 教育担当は、その時点のコードに **画面上は変化が見えず、特定の条件だけが偽になる変更を 1 箇所** 入れたブランチを用意する。読めば分かる変更（明らかな typo、`&& false` のような式）にはしない。出力して確かめないと分からない変更にする。
- 壊す場所は段階ごとに深くする（条件そのもの → 条件の材料 → 材料を作っている別レイヤー）。
- 学習者は「画面だけで切り分け → 出力で絞り込み → 原因の行」の順で進め、辿った経路を PR に書く。原因の行だけを書いた PR は差し戻す。

### 差し込み候補（学習のチャンスがあれば Issue にする）

- oxlint の設定を読む、ルールを 1 つ追加する（`no-console` など）
- Prettier の導入と、保存時フォーマット
- `tsconfig` の `strict` と、型エラーを意図的に起こして読む
- GitHub Actions で lint と build を PR ごとに回す
- `git rebase` でブランチを main に追従させる、コンフリクトの解消
- `README` に画面と構成の説明を追記する（Phase の節目ごと）

## 目標成果物の仕様（要約）

- 月ごとの明細一覧。前月・翌月で切り替え。今月には「今月」バッジ
- 収入・支出・残高のサマリ
- 明細の追加（ダイアログ）、編集・削除（明細詳細ページから、削除は確認ダイアログ）
- 備考（textarea、200 文字まで、改行可）
- 未分類の明細があれば警告バナー。未分類の行は背景色を変える
- 「今月を締める」ボタンは、下の業務ルール 1 を満たすときだけ表示する。条件を満たさないときは理由を出さず非表示にする
- 締め済の月は追加・編集・削除できず、「締め済」バッジが付く
- カテゴリ別の月予算を「カテゴリ別予算」カードに表示し、超えたカテゴリには「超過」バッジと警告バナーを出す
- 今月、カテゴリ一覧、カテゴリ別の予算は、最終的には API（偽 API）から取得する

### 業務ルール

アーキテクチャ（Phase 9）で core に集まるルール。いずれも React にも API にも依存しない純粋な判断として実装する。

| # | ルール | 入力 | 画面での現れ方 |
| --- | --- | --- | --- |
| 1 | 今月を締められるのは、表示月が今月、未締め、未分類が 0 件、かつ前月が締め済（前月に明細がなければ不要）のとき | 表示月、今月、締め済の月、全明細 | 「今月を締める」ボタンの表示 |
| 2 | 明細の日付は、締め済の月と、今月より先の月には登録できない | 日付、今月、締め済の月 | フォームの日付項目のエラー |
| 3 | 10,000 円以上の支出は備考が必須 | 種別、金額、備考 | フォームの備考項目のエラー。一覧と詳細の「高額」バッジ |
| 4 | 締め済の月の明細は追加・編集・削除できない | 明細の月、締め済の月 | 詳細ページのボタン非表示、フォームの非表示 |
| 5 | カテゴリ別の月予算を超えたら警告する。超過しても締めは妨げない | 表示月の明細、予算 | 「カテゴリ別予算」カードの超過バッジ、警告バナー |

入力形式のチェック（必須、1 円以上、200 文字以内、日付の形式）はこの表に含めない。それらは zod スキーマの責務で、業務ルールではない。
