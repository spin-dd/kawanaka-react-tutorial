# PR レビューの書き方

教育担当が PR をレビューするときの方針です。Claude がレビュー案を作るときも、これに従います。

## 構成

レビューは、次の順に書きます。依頼はすべて番号を付け、最後のチェックリストと 1 対 1 で対応させます。
評価と依頼が混ざると、学習者が修正や再回答で漏れを出しやすくなるためです。

1. **良かった点**: 評価だけを書く。依頼は混ぜない。
2. **コードの修正をお願いしたいこと**
3. **PR の説明欄に追記をお願いしたいこと**
4. **再レビューを依頼する前のチェックリスト**

- 「任意」は使いません。直してほしいものは依頼に入れ、直さなくてよいものは書きません。「任意」と書くと、学習者はたいてい何もしません。
- 書かなくても伝わる補足（「問 2 は書き直さなくてよい」など）は書きません。

## 指摘の書き方

初学者は、何が問題なのかがわかっていないことが多いです。いきなり問いを投げられても、何を答えればよいかがわからず、負担になります。
そのため、**まず問題を示します**。何が起きているか（画面で確かめられる症状など）と、なぜよくないかを書きます。

そのあとの書き方は、次の 2 つから選びます。

- **直し方の方針を書く**: 基本はこちらです。理由がわかったうえで自分で直すことにも、学習の意味があります。名前の例示（`headerRight` など）までは書いてかまいません。修正コードは書きません。
- **問いで終える**: 直し方を書くとそれがそのまま答えになり、学習の意味がなくなる場合は、問題の指摘と問いで終えてかまいません。

### 問いの立て方

問いで考えさせるときは、オープンすぎる問いにしません。**何を見て、何と比べて、何を答えればよいか** がわかる問いにします。

| 避ける | 使う |
| --- | --- |
| 「このクラスがすべて枠のものか、考えてみてください」 | 「目標成果物の明細一覧の枠を参考に、`Card` のクラスを『枠のもの』と『サマリカードの並べ方のもの』に仕分けてください」 |
| 「要素の種類が変わってよいか、考えてみてください」 | 「`<h2>` を `<p>` に変えたのは意図してですか。意図があれば理由を、なければ戻してください」 |

意図がわからない変更は、考えさせるのではなく、本人の意図を聞きます。

## 確認問題の書き直し依頼

- ほかの指摘で理解がカバーされている問いには、書き直しを求めません。
- 書き直しを求めるときは、何を書き足せばよいかを具体的に示します。

## Issue 側に誤りがあったとき

Issue の前提が実装と食い違っていたら、学習者に気づかせる材料にはせず、教育担当のミスとして扱います。実務で仕様の誤りを伝えるときと同じです。

- Issue に訂正コメントを入れる。誤っていた点、訂正後の内容、訂正後の完了条件を書く。
- PR のレビューでは、冒頭で一言謝り、訂正コメントを見てやり直すよう案内する。

## デバッグ課題の PR

デバッグ課題では、原因の場所を言わないことが前提です。「指摘の書き方」の「まず問題を示す」「直し方の方針を書く」は当てはめず、問いで導きます。
ただし、ここでも問いはオープンにしすぎず、何を見ればよいかがわかる問いにします。
